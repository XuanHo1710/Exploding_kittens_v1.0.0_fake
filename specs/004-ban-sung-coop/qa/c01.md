## Cross-Check Findings

### [MAJOR] F1 — Free Co-op Victory (`pot === 0`) only credits `acc.wins` to MVP, dropping all other teammates (`game.ts` → `rooms.service.ts` → `accounts.service.ts`)
- **Mismatch:**
  - On `w.result.victory === true`, `Game.syncBansung()` (`server/src/game/game.ts:1862-1869`) sets `this.winnerIds = ranked.map((p) => p.id)` (all active non-left humans) and `this.winnerId = mvpId || ranked[0]?.id` (single MVP), and populates `this.payouts` only when `this.pot > 0 && ranked.length > 0` (`this.payouts` stays `{}` when `pot === 0`).
  - `RoomsService.payout()` (`server/src/game/rooms.service.ts:298-329`) switches on `hasCustomPayouts = Object.keys(game.payouts).length > 0`.
  - When `pot > 0`, `hasCustomPayouts` is `true`, so `accounts.rewardPayouts(game.payouts, game.winners(), opId)` (`server/src/store/accounts.service.ts:251-293`) increments `acc.wins++` (L288) for every player in `game.winners()` (`this.winnerIds`) and `pushAccount(p.id)` updates every player (`rooms.service.ts:319`).
  - When `pot === 0` (default free room), `hasCustomPayouts` is `false`, so `RoomsService.payout()` falls into `else if (w)` (`rooms.service.ts:321-329`) and calls `accounts.rewardWinner(w, pot, opId)` (`accounts.service.ts:231-244`) + `this.pushAccount(w)`. `rewardWinner` increments `acc.wins++` solely for the single `w` (`this.winnerId`), silently dropping `wins` and `pushAccount` for all other co-op winners in `game.winnerIds`.
- **Why tests missed it:** `server/test/bansung-net-security.test.cjs` `4b` (`L1111-1255`) tests paid co-op matches (`bet = 100` / `bet = 200`) and does not assert `acc.wins` for multi-player `bet = 0` (`pot === 0`) victories.

### [MAJOR] F2 — Rate-limiter / abuse-kick and envelope security checks are unhooked at the gateway (`game.gateway.ts` / `game.ts` vs `bansung/security.ts` & `d48`)
- **Abuse-kick never disconnects sockets & non-kick command rejections ack `{ ok: true }`:**
  - `BansungWorld.enqueueCommand()` (`server/src/game/bansung/world.ts:1255-1278`) tracks sliding-window violations (`VIOLATION_KICK_COUNT = 20` within `VIOLATION_WINDOW_MS = 5000` in `server/src/game/bansung/security.ts:47-48`) and returns `{ ok: false, reason, shouldKick }`.
  - `Game.bansungCommand()` (`server/src/game/game.ts:1800-1803`) only throws `GameError` when `!res.ok && res.shouldKick`; `GameGateway.handle()` (`server/src/game/game.gateway.ts:374-376`) turns `GameError` into `toast` + `{ ok: false, error }` without calling `client.disconnect(true)` (unlike `d48` §2 L49 and expired auth at `game.gateway.ts:369`), allowing abusive sockets to remain connected and keep flooding.
  - Meanwhile, non-kick rejections (`rate_limit`, `tick_cap`, `life_state_blocked`, `invalid_gacha_pick`, `unknown_command`, etc.) do not throw or return an error in `Game.bansungCommand()`, so `GameGateway.bansungCmd` (`game.gateway.ts:325-333, 372`) responds with `{ ok: true, result: undefined }` (vs `{ ok: false, error: 'rate_limited' }` in `d48` §2 L48).
- **`config` rate-limit bucket (`5` burst / `1/s` refill) and `bansung:hero` throttling are unused in production:**
  - `server/src/game/bansung/security.ts:42-43, 376, 405-483` defines `CONFIG_BUCKET_CAP: 5`, `CONFIG_REFILL_PER_SEC: 1`, and `BansungRateLimiter.consume(playerKey, 'config', ...)`, but `consume(..., 'config')` is never called outside unit tests (`server/src` has zero callers). Neither `GameGateway.bansungConfig` / `bansungHero` (`game.gateway.ts:335-348`) nor `RoomsService` / `Game` throttles `bansung:config` or `bansung:hero`, allowing unbounded `rulesVersion` bumps / ready resets / `addLog` / `state` broadcasts.
- **Unchecked outer `{ config }` wrapper in `GameGateway.bansungConfig`:**
  - `Client` (`Lobby.tsx:172`) sends `{ config: { ... } }` and `GameGateway.bansungConfig()` (`game.gateway.ts:338-341`) unwraps `body.config` whenever `Object.hasOwn(body, 'config')` without running `isSafePlainObject`, extra-key rejection, or JSON byte budget checks on the outer wrapper `body` (unlike `room:create` at `L91-98` and `room:rules` at `L112-114` which reject unknown wrapper keys).
- **Why tests missed it:** `bansung-net-security.test.cjs` `3c` (`L886-926`) exercises `rl.consume('p0', 'config', ...)` directly on `BansungRateLimiter` and checks only that `Game.bansungCommand()` throws `GameError`; socket integration `1b` sends only single valid `bansung:config` / `bansung:hero` events without testing socket disconnection or config/hero flooding.

### [MINOR] F3 — Shared Constant/Event Parity, Bot Ceiling Drift & Config Coercion (`shared/src/protocol.ts`, `shared/src/bansung/types.ts`, `server/src/game/game.gateway.ts`, `server/src/game/game.ts`)

- **Unused `BANSUNG_LOBBY_MAX_PLAYERS` (`4`) & bot cap divergence from `d03`/`d48`:** `shared/src/bansung/types.ts:22-24` exports `BANSUNG_MAX_PLAYERS = 10`, `BANSUNG_LOBBY_MAX_PLAYERS = 4`, `BANSUNG_MAX_BOTS = 4`. `BANSUNG_LOBBY_MAX_PLAYERS` has zero references across `shared/`, `server/`, and `client/` (`GAME_MODES.bansung.maxPlayers = 4` in `shared/src/protocol.ts:79` caps lobby human seats instead), while `normalizeBansungConfig()` (`shared/src/bansung/types.ts:173`) clamps bots against `BANSUNG_MAX_PLAYERS` (`10`) rather than `4` (allowing up to 4 humans + 4 bots = 8 squad members, whereas `d03`/`d48` §3 specified `humans + bots <= 4`).
- **Stale `GAME_MODES.bansung.desc` & `validateBansungConfig` enum coercion:** `shared/src/protocol.ts:80` still describes `'10 đợt quái & 3 Boss'` even though `resolveBansungGameMode()` (`shared/src/bansung/types.ts:199-201`) defaults to `'survival'`. Also `validateBansungConfig()` (`server/src/game/bansung/security.ts:335-346`) delegates to `normalizeBansungConfig()` rather than rejecting unknown keys or invalid enums with `GameError` (unlike `validateBansungHero()` at `L353-370` and `d48` §3 L76).

## Verdict: FAIL
